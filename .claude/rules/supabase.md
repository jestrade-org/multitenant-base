# Supabase

Applies to: `supabase/`, `packages/*/src/infrastructure/supabase/`.

## Division of responsibility

The React client talks to Supabase **directly only** for:
- Auth (sign in/out, session refresh)
- Realtime subscriptions (read-only)
- Storage uploads/downloads via signed URLs

**All business reads and writes go through the Node API**, so invariants live in one
place. A React component must never insert or update a business table.

## Keys

| Key                 | Where it may exist                     |
|---------------------|----------------------------------------|
| `anon` key          | Browser bundle. Public by design — it is only safe because RLS is correct. |
| `service_role` key  | Node API process memory only. Never in the browser, never in an edge function that returns user data, never in a log, never in a client-visible env var, never in git. |

If a `service_role` key is ever exposed, treat it as an incident: rotate immediately,
audit access logs, document in the postmortem.

## Row Level Security

**RLS is enabled on every table. Always. A table without policies is a bug.**

```sql
alter table projects enable row level security;
alter table projects force row level security;  -- applies to table owners too

create policy projects_select_own_company on projects
  for select using (company_id in (
    select company_id from company_members where user_id = auth.uid()
  ));
```

Rules:
- Separate policies per operation (`select`, `insert`, `update`, `delete`). Never a
  single `for all` policy — it hides intent and over-grants.
- Deny by default: no policy means no access. Never write `using (true)` on a
  tenant-scoped table.
- `with check` on every `insert`/`update` policy, or a user can write rows into another
  company.
- Index every column referenced in a policy — policies run per row.
- Wrap membership lookups in a `security definer` function marked `stable` to avoid
  recursive policy evaluation and repeated subqueries.
- `service_role` bypasses RLS. That is exactly why the API must do its own
  authorization check before every query — see `@.claude/rules/security-iaaa.md`.
- **Every tenant-scoped table ships with a test** proving a member of company A cannot
  read, update, or delete company B's rows. No test, no merge.

## Types & mapping

- Generate types into
  `packages/<context>/src/infrastructure/supabase/database.types.ts`:
  ```bash
  supabase gen types typescript --local > .../database.types.ts
  ```
- Never hand-edit generated files; regenerate after every migration in the same commit.
- Generated row types **stay in `infrastructure/`**. Explicit mappers convert rows to
  domain objects and back. A generated type must never appear in `domain/`,
  `application/`, or React props.

## Auth

- Verify the JWT **server-side** on every request (signature, `exp`, `aud`, `iss`).
  Never trust a `user_id` sent in a body, header, or query param.
- Derive the acting user and company from the verified token, always.
- Configure token lifetimes deliberately: short access tokens, rotating refresh tokens,
  refresh token reuse detection enabled.
- Enable leaked-password protection and MFA for administrative roles and any role that
  can move money.
- Email templates are Spanish; their keys and file names are English.

## Storage

- Buckets are **private by default**. Public buckets require written justification.
- Access via short-lived signed URLs generated by the API after an authorization check.
- Bucket policies scope objects by path prefix: `{company_id}/{entity}/{file_id}`.
- Validate on upload: content type sniffed from bytes (not the client-supplied header),
  size limit, extension allowlist per document kind (for example PDF/XML/images only).
- Never serve user-uploaded content from the app's own origin without
  `Content-Disposition: attachment` and a restrictive CSP.

## Realtime

- Realtime respects RLS — but only if RLS is right. Verify per channel.
- Subscribe to specific tables and filters, never a firehose.
- Treat realtime as a cache-invalidation hint: refetch through the API rather than
  rendering the payload as authoritative.
- Always unsubscribe on unmount.

## Edge functions

- Use them only for webhooks and provider callbacks that must not traverse the API, or
  for latency-critical public endpoints. Business logic stays in the domain packages.
- Verify webhook signatures before doing anything else, and reject on clock skew.
- Idempotent by construction: dedupe on the provider's event ID.
- Never return data derived from `service_role` access without an authorization check.

## Local development

- `supabase start` for a local stack. All development and tests run against local,
  never against production or a shared staging database.
- Seed data lives in `supabase/seed.sql`, uses synthetic fixtures, and contains
  **no real customer data**. Production dumps never land on a developer machine.
